# Sidecar 轻量领域建模设计

日期：2026-10-14。状态：待用户审阅，尚未实施。

## 目标与范围

用户已确认采用上一轮建议的轻量 DDD：集中任务状态、取消和恢复规则，明确队列与执行状态的职责，并把核心规则与 SQLite、Android、LangGraph 隔离。成功标准是规则可独立测试，现有 CLI、HTTP、聊天入口及持久化任务继续兼容。

本次保留单进程部署结构、后台 worker、LangGraph、现有数据库结构和状态字符串。不引入微服务、CQRS、事件溯源、通用 Repository 框架或新依赖，不按外部 App 划分领域，也不全面重排目录。设备动作及敏感控件识别不在此次重构范围。

## 方案选择

推荐抽取纯领域规则，并增加一个窄的执行控制服务。只统一常量不足以消除规则散落；全面引入聚合、仓储和事件总线则会扩大兼容风险。领域对象采用小型不可变结果或纯函数，不复制整个 LangGraph 状态，也不把原有 Task 输入模型直接升级成包含全部执行细节的巨大聚合。

## 状态归属

| 数据 | 职责与权威范围 |
| --- | --- |
| queue.sqlite 的 jobs | 排队顺序、领取权、队列控制请求、对外任务生命周期；executing 表示 worker 已领取，不等同于执行器正在发出动作 |
| tasks.sqlite 的 tasks | 执行现场索引、已确认控制结果和执行证据；恢复前用于核对任务、设备与终态 |
| checkpoints.sqlite | LangGraph 的可恢复程序位置；不得覆盖已确认取消，也不得作为重放旧 GUI 动作的授权 |
| actions 日志 | 动作意图及不确定结果；保留人工核对后再恢复的现有机制 |

不宣称三个数据库具有跨库原子性。队列决定调度，执行索引提供执行事实；worker 启动对账弥合中断窗口。查询期间，队列为 executing 且存在执行索引时，继续展示执行索引的状态；控制请求未确认时继续使用 pending_control。

## 领域规则模块

新增 `src/sidecar/lifecycle.py`，仅依赖 Python 标准库，集中表达以下规则：

- 终态为 completed、failed、cancelled；队列可恢复状态为 paused、waiting_user、interrupted。
- 领取只允许 queued → executing；暂停与等待用户继续保留执行环境使用权。
- 队列暂停/取消：executing 时只登记请求，等待执行边界确认；其他非终态可立即转换为 paused/cancelled。
- 取消请求具有粘性，不能被后续暂停、清空控制或恢复覆盖。
- 队列恢复需合法状态和有效核对备注，重新进入 queued；执行器恢复还需设备相符、索引及检查点均非终态，并优先处理取消请求。
- 执行边界优先级维持取消、暂停、运行预算耗尽；时钟读取由调用方提供。
- 队列收尾保留既有终态；非终态中已接受的取消优先于迟到的执行结果。
- 执行索引写入保留现有取消覆盖语义，包括队列完成写回前接受取消的窗口。不能把“所有终态均不可修改”机械套到 Store.save 上，否则会破坏现有跨库取消规则。
- worker 对账区分引擎已有终态、队列已有终态但引擎未结束、未处理取消、遗留 executing，以及需保留的暂停/交接现场。规则返回决策，调用方执行数据库和日志操作。

校验错误在边界保留现有异常类型与面向用户的提示；不借此次重构收紧与任务无关的输入协议。完整状态转移应按具体用例表达，而不是允许任意调用者执行通用 set_status。

## 应用与基础设施边界

新增 `src/sidecar/execution_control.py`，负责提交控制请求、在适当情况下确认取消，以及孤立执行任务的工作区释放。依赖一个只暴露所需存储操作的 Protocol，现有 Store 直接满足该接口，不新增转发式仓储包装。

`Harness.control` 保留原方法签名，委托控制服务。`JobQueue.control/clear` 使用同一个服务，不再为了发送信号构造 OfflineDevice、OfflinePolicy 和完整 LangGraph。服务保留事件记录、锁和并发终态检查的现有语义。

`Harness` 继续负责观察、决策、动作执行、验证、图中断和恢复编排；在取消、恢复及边界判断处调用领域规则。恢复后清除旧动作并从新观察开始的行为不变。

`JobQueue` 继续作为现有入口，承担提交与查询用例和 SQLite 操作。此次不拆成一整套仓储层；将生命周期决策交给领域模块，同时在现有事务内读状态、计算决策、写回。

`Store` 负责 SQL、锁和动作日志，将取消覆盖决策委托领域规则，但保留 BEGIN IMMEDIATE 及 SQL 层取消粘性保护。纯规则替代不了事务原子性。

`worker` 执行对账决策，继续保留模型/设备创建与任务启动逻辑。`contracts.py` 中已有 Task、Action、Verification 行为和 Device/DecisionModel 接口继续使用，不为目录层次而搬迁。

## 兼容与恢复约束

- 不改数据库 schema、任务标识、事件名称、对外响应字段和状态字符串。
- 保留 Harness、JobQueue、Store 的现有调用入口；需要迁移 TERMINAL 引用时在原模块保留兼容导出。
- 保留已接受取消优先、重复提交去重、清空队列覆盖全部未结束任务等现有行为。
- 保留恢复前人工核对，不重新规划任务，不重放旧动作，不把恢复理解为最终提交授权。
- 保留执行锁和现有锁顺序；对账或控制服务抽取不得使其他任务提前领取环境。
- 历史数据库能够直接打开并恢复；新增领域对象不进入已保存 JSON，不要求数据迁移。

## 验收

先运行现有核心测试建立基线，新增规则测试先验证失败，再实现对应规则。纯规则测试不创建数据库、设备或 LangGraph，覆盖状态合法性、取消优先级、恢复资格和对账分支。

集成回归重点复用并按缺口补充：

1. 取消后到达的暂停、恢复和完成结果不能撤销已接受取消。
2. 引擎完成与队列收尾之间收到取消，重启前后均得到一致结果。
3. 动作已产生副作用但进程中断时，恢复不会重复动作。
4. 暂停和等待用户仍阻塞后续任务，取消孤立任务后释放工作区。
5. 批量清空在解除队列占用前先处理执行器信号，保留全部历史和证据。
6. 第一个检查点前崩溃、队列终态但引擎非终态等组合可按现有语义对账。
7. CLI、HTTP、OpenAI 兼容入口输出与错误行为保持一致。
8. 队列控制不再构造模型、设备或 LangGraph；用边界测试确认此依赖已经移除。

实施后运行离线自动化测试及代码检查。真实设备测试需设备与账号环境，仅在条件具备且确有相关改动时运行；报告中明确区分通过、跳过和未执行。新增代码遵循格式检查，但不顺带改动无关文件。
