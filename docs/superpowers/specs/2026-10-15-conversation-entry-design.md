# Sidecar 对话入口设计

日期：2026-10-15

状态：方案范围已确认，待书面设计审阅。

## 目标

用户希望 Sidecar 能自然处理问候、时间查询和一般对话，并根据上下文决定何时需要操作手机。第一版包含统一对话入口、真实时间工具、近期对话与任务上下文、按需进入现有手机执行器。

成功标准：设备断开或 worker 不在线时，模型配置正常的聊天与报时仍然可用；只有手机任务进入设备队列。普通回复不创建任务、不启动 App、不截图。

## 当前实现与调整位置

- `openai_compat.py` 已有固定问候、帮助、队列查询与明确任务控制命令。普通输入最终进入 `submit_goal`；虽然请求包含 messages，目前只使用最后一条用户文本做任务决策。
- `model.py` 的规划、决策和验证均针对 GUI，不能直接承担普通聊天。
- `worker.py` 负责手机执行与恢复，继续复用。
- 网页当前是结构化任务表单，通过 `/api/tasks` 提交。新增轻量对话入口，结构化任务表单保持明确提交任务的语义。

## 方案选择

采用一个模型驱动的对话决策层，直接复用现有模型提供商配置。相比不断扩充关键词，能够理解表达变体、混合请求和上下文；相比拆成多个 agent，组件和模型调用更少。普通问答在一次决策调用中直接返回答案。

对话服务与设备 worker 分离。新模块 `conversation.py` 管理输入归一化、上下文、结构化决策和时间工具；模型适配层增加独立对话调用，不附加 GUI 专用系统提示。服务端负责校验并分发结果，模型不能直接执行队列控制或设备操作。

## 输入与输出契约

对话输入包含当前消息、近期 user/assistant 历史、用户时区、显式请求标识，以及可选的目标 App。限制消息数量和总字符数；送入模型时保留最近最多 12 条消息，总计最多 16000 字符，单条最多 4000 字符。客户端 system 消息不替换服务端能力与执行约束。

决策为以下互斥类型，使用 Pydantic 校验不同类型的必填字段：

| 类型 | 必填内容 | 后端行为 |
| --- | --- | --- |
| reply | answer | 直接回复 |
| clarify | question | 请求缺失信息，不创建任务 |
| time | IANA timezone | 调用时间工具，按真实结果生成回复 |
| device | standalone_goal | 校验目标 App 后交给现有任务队列 |

device 可附带简短回应，用于“你好，顺便设置闹钟”等混合请求。standalone_goal 必须包含执行所需的完整上下文，不能新增用户未请求的动作。原始消息与解析后目标同时记录以便追溯；不把原始含糊短句直接交给 GUI 规划器。

## 时间与能力边界

时间由运行服务的系统时钟读取，通过标准库 zoneinfo 转换，结果明确包含日期、时间、时区。默认时区为可配置的 `SIDECAR_TIMEZONE`，未配置时使用 Asia/Shanghai；启动时验证配置。用户明确要求其他地区时采用对应有效 IANA 时区，地点不明确时询问。

time 路径由后端根据工具结果直接构造时间答复，避免模型编造数字。时间不作为长期缓存回答。模型提示区分一般报时与检查手机时钟设置；后者属于 device。

第一版没有天气、搜索能力。模型必须根据实际能力回答，不得虚构查询结果。模型连接失败时给出可理解的错误，禁止退回“默认创建手机任务”。离线 demo 保留现有演示任务行为，并明确普通智能对话需要模型配置，不假装具备离线语义理解能力。

## 上下文与任务关联

OpenAI 兼容接口使用客户端提供的近期消息，不将不同客户端的聊天混成全局历史。网页对话在当前浏览器会话中保存近期消息，断开配对时清除，不新建跨会话长期记忆系统。

任务上下文只读取本轮对话关联的任务编号，并从队列加载真实状态、原始目标和必要结果摘要；不把客户端声称“任务成功”的文本当作事实。没有关联任务时不自动选取全局最新任务。

“刚才完成了吗”可根据关联任务的真实状态回答。“改成八点”若明确关联已完成闹钟任务，则生成完整的新修改目标；多个候选或原任务仍在运行时询问如何处理，不擅自修改、重启或重复提交正在执行的任务。暂停、取消、恢复继续使用现有明确命令及状态检查，不因聊天历史自动授权恢复。

## 接入与兼容

`/v1/chat/completions` 的流式与非流式路径都调用同一对话服务。明确帮助、队列查看及现有控制命令先沿用确定性处理；普通消息交给模型决策，替换固定问候白名单。信息回复继续使用 `task_id: null`，不显示手机任务完成的措辞。

新增已鉴权的 `/api/chat`，网页增加独立的简洁对话区域，显示用户和助手消息，并在生成设备任务时关联现有任务详情。原 `/api/tasks` 及带验收条件的结构化表单保持兼容。

新入口复用既有鉴权、错误清洗与模型超时策略。对话请求不检查 Android 连通性、不取得设备执行锁，不等待 worker 才能回答。

## 重试与幂等

沿用兼容端点显式 Idempotency-Key 或完整对话指纹的语义。对于生成手机任务的决策，持久化原始请求指纹、解析后目标和任务编号，重试先查已存在的映射，不重新生成另一个目标或任务。相同显式 key 携带不同输入应返回冲突。数据库事务和唯一键保证并发请求只创建一个任务，记录与任务创建需要原子提交。

普通信息回复不进入设备 jobs；报时每次读取真实时钟。模型调用不持有数据库写锁。

## 验证

新增有行为意义的测试，先验证失败再实现：

1. 问候变体和一般问答返回信息，设备构造、App 启动和任务提交均未发生。
2. 固定测试时钟覆盖默认时区、跨日期转换和无效时区；返回时间来自工具。
3. 设备断开、worker 停止时聊天可用；模型失败不会转成设备任务。
4. 混合请求只创建一个正确任务；“改成八点”使用相关历史，歧义请求不创建任务。
5. 任务状态查询读取真实队列，客户端历史不能伪造完成状态。
6. 流式、非流式与网页 API 的路由一致；普通回复 task_id 为空。
7. 并发重试和进程重启后不重复创建设备任务，同 key 不同输入冲突。
8. 现有明确控制指令、任务恢复、App 白名单和 GUI 验证测试继续通过。

不以真实模型输出作为单元测试固定断言；使用可注入模型与时钟。完成后运行相关接口、队列、模型和前端测试及项目静态检查。真实设备验收单独报告是否执行，不以模拟通过替代真机结论。

## 范围与实施注意

不引入多 agent、联网搜索、长期记忆或自动更改运行任务。当前工作区已有大量未提交修改，实施时以现有文件为基准逐处合并，不覆盖这些变更；本设计单独提交。
