# 结果验证与交接输出规范

资料类型：项目维护的 Agent 行为规范与验收参考。
来源：项目所有者提供的面试作业“结果可验证”要求，以及当前执行与验证接口。
整理日期：2026-10-15。
适用范围：Sidecar 完成判定、人工交接和对外结果表述。
接入状态：本文是详细知识资料；核心运行规则已整理为 `src/sidecar/assets/verification-policy.md`，随安装包加载到决策与验证提示词，并在验证记录中保存规则摘要。外部知识库不是规则来源，不能依赖检索是否命中。

## 1. 完成判定

只有用户要求的结果在指定 App、设备及适用账号中有当前证据，才可以报告“已完成”。点击成功、模型计划、历史成功记录、按钮存在、知识库示例均不是本次完成证据。

完成前获取新观察，对原始完成标准逐项核对，不得省略、偷换或降低标准。证据不足、不可见、存在矛盾或仅能推测的项目均标记为未通过。每项通过结果应说明实际看到的内容，而不只写“成功”或“已核对”。

应按场景选择有效证据：

| 场景 | 应核对的事实 | 不足以宣布完成的信号 |
| --- | --- | --- |
| 设置闹钟 | 时间、AM/PM、开启状态；必要时重新打开列表确认保存 | 时间选择器中选中了目标时间 |
| 创建待办 | 目标清单、事项文字、已保存的列表记录 | 输入框已有文字 |
| 保存草稿 | 目标草稿及内容已保存，未执行发送 | 编辑页出现发送按钮 |
| 用户手动发送后核对 | 正确收件人、内容及可见发送成功或已发送记录 | 用户按过按钮、仅口头说已发送 |
| 用户手动支付后核对 | 目标订单、金额及支付成功状态 | 停留在支付页、支付按钮可见 |

表中是验收指导，不代表项目已经逐项实现 App 专用验证器。最后两类仍需用户执行最终提交；本规范不会授予 Agent 自动发送或支付的权限。

## 2. 人工交接边界

交接结果应分别说明：已经验证的部分、尚未完成或不能确认的部分、需要用户做什么。

只有准备条件全部具有证据、剩余动作确实只是用户最终提交时，才能报告“准备已完成，等待你确认”。收件人、内容、金额、商品、地址等准备项缺失或不确定时，应报告“准备尚未全部完成或无法确认”。仅出现发送/支付按钮，不证明准备已完成。

用户要求“保存草稿”时，已保存且未发送即可能满足任务；不能擅自扩大为“发送邮件”。用户要求最终发送/支付时，停在确认页不得报告整个任务完成。回复“继续”表示重新观察和核对，不解除最终提交限制。

遇到登录、验证码、设备错误或未知动作结果时，可先停止并请求用户介入；如果无法取得新证据，必须说明“当前无法验证”，不能把一般交接包装成已验证的阶段完成。

## 3. 输出结构与示例

建议结构：状态 → 已核对结果 → 执行范围与证据 → 未完成事项 → 用户下一步。只展示有来源的内容，不捏造截图、观察编号或成功状态。

以下文字是模板示例，不是任何当前任务的执行结果：

- 已完成：“已在执行端 Google 时钟中确认 23:58 闹钟存在且已开启。结果保存在该 Android 实例中，不代表 iPhone 系统闹钟已设置。”
- 准备已验证：“已核对收件人、主题和正文；邮件尚未发送。请在 App 中核对后手动发送，随后继续以核对结果。”
- 准备未完成：“已填入正文，但尚未确认收件人。邮件未发送，当前不能认定准备完成，请先核对收件人。”
- 无法验证：“本次操作返回结果不确定，尚不能确认是否保存成功。请先检查 App 现场，避免重复创建。”

控制台报告接口与聊天入口共用结果格式函数，逐项证据来自任务记录；模板示例不直接替换实际结果。

## 4. 与提示词、程序及知识库的关系

- **程序约束**：Harness 必须经过新的验证观察才能进入 completed；Verification 核对标准覆盖、通过标志、证据非空和确认边界。取消、设备权限与禁止盲目重放由程序执行。
- **系统提示词**：持续要求依据新观察核验、证据不足则不通过、按钮存在不等于准备完成。它属于受维护的规则配置。
- **知识库资料**：保存各 App 的验证方法、界面含义、失败案例和合格输出示例；检索内容是参考数据，不能覆盖用户目标、程序规则或增加操作授权。
- **本次执行证据**：截图、控件状态、观察编号、时间和任务记录应随任务保存；它们不能被历史知识库内容替代。对截图的模型判断仍可能错误，关键场景应增加确定性检查或独立复核。

如果以后接入 Dify/MCP，应保留资料来源和版本，将检索结果放在参考资料上下文，禁止把任意检索正文提升为系统指令。不要把用户私人截图、账号内容或原始执行日志默认上传知识库；可整理经核对、去除私人信息的案例。

## 5. 当前实现和缺口

截至本次源码核对：完成前新观察、逐项验证、最终提交交接、草稿任务边界和证据展示已实现。Google 时钟有单次真实成功与重开核对记录，见 [演示指南](../clock-demo.md)。相关 Harness 验证回归为 9 项通过；它们不替代真实 App 验收。

目前的结构校验不能独立证明模型填写的 evidence 与画面一致；普通登录/故障交接也不统一附带逐项完成证据。真实发送、支付、多 App 稳定性以及跨端同步不可从闹钟样本推断。Dify/MCP 仍为设计草案。运行规则通过受维护的包内资源加载，详细资料与外部检索不直接进入系统指令。
